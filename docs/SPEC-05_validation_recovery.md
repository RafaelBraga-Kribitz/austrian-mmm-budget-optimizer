# SPEC-05 — Validation & Recovery Testing

The credibility engine (Q1). Requirement IDs: `VR-xxx`. Code in `src/ambo/validate/`.
Layer R results are publishable ONLY after §3 passes (Charter E-2).

---

## 1. Artifacts

`reports/recovery/RECOVERY_REPORT.md` (generated, with embedded tables/PNGs) +
`exports/roas_summary.csv` + `exports/response_curves.csv` + SSOT rows.

## 2. What "recovery" is measured against

`truth.json` per scenario (SIM §8): true average ROAS, true response-curve samples,
true contribution shares, true adstock half-lives. Comparisons are on OBSERVABLE
quantities (ROAS, curves, shares) — NOT on raw K/s parameters (AGENTS T-5).

## 3. Recovery gates (per scenario; all must pass at M3)

| Gate | S-A (clean) | S-B (realistic) | S-C (hostile) |
|------|-------------|-----------------|----------------|
| VR-301 ROAS coverage: true average ROAS inside 90% HDI | ≥ 5 of 6 channels | ≥ 4 of 6 | ≥ 4 of 6 (incl. the zero channel, see VR-304) |
| VR-302 ROAS ranking: Spearman(posterior-median ROAS, true ROAS) | ≥ 0.83 | ≥ 0.7 | not gated (5 effective channels) |
| VR-303 Response-curve shape: mean absolute error between posterior-mean curve and true curve over the observed-spend grid, as % of true curve max | ≤ 15% per channel, ≤ 10% median | ≤ 25% / ≤ 15% | reported, not gated |
| VR-304 False-positive control (S-C only): `display_video` | — | — | posterior P(average ROAS < 0.2) ≥ 0.7 AND its median contribution share ≤ 3% |
| VR-305 Half-life direction: posterior median half-lives rank print/radio above search channels | required | required | required |
| VR-306 Contribution decomposition: total media share of revenue within ±10 pp of truth | required | required | required |

- VR-310: Gates are tuned to be passable by a correct implementation and failed by
  the classic bugs (T-2 convolution, T-1 scaling, leakage). If a gate fails: debug
  order = transforms (MD-070) → scaling round-trip → data joins → sampler health.
  Widening any gate requires an ADR that names the suspected structural cause.

## 4. Holdout (all scenarios + Layer R)

- VR-401: Refit on the first T−13 weeks, predict the last 13 (with actual spend as
  input — conditional forecast), report MAPE + 90%-interval coverage vs. a
  seasonal-naive baseline (revenue_{t−52}). Model must beat naive MAPE on S-A/S-B;
  on Layer R the result is reported either way (n=13 caveat mandatory).

## 5. Sensitivity suite (Layer R centerpiece; also run on S-B for reference)

- VR-501: Prior-influence: refit Layer R with `priors_synthetic.yaml` (weak) vs frozen
  `priors_real.yaml` (elicited). Artifact: forest plot of ROAS posteriors under both,
  per channel + one paragraph on where elicitation moved/narrowed estimates — the
  "what your agency experience is worth in bits" chart. THE portfolio artifact of
  this project (`reports/recovery/vr_prior_influence.png`).
- VR-502: Leave-one-channel-out: drop the largest-spend channel, refit, report how
  its contribution gets re-attributed (collinearity honesty check).
- VR-503: (Layer P S-B) same prior swap — demonstrates that with 104+ clean-ish weeks
  the data dominates the priors; contrast with Layer R in one combined figure.
- VR-504: No-promo sensitivity (Charter R-9): Layer R refit without the promo
  regressor; report ROAS shifts; feeds LIMITATIONS.

## 6. Baseline + cross-check

- VR-601: OLS baseline: revenue ~ same regressors with adstock fixed at prior-mode λ
  and no saturation, HC1 errors. Report side-by-side with Bayesian results on S-B:
  expected outcome — unstable signs/absurd magnitudes on collinear data; whatever
  happens is reported. Purpose: show why the Bayesian machinery earns its complexity.
- VR-602: pymc-marketing cross-check (S-B + Layer R): fit their `MMM` class with
  matched transforms/priors as closely as its API allows; gate: channel ROAS
  posterior medians correlate ≥ 0.8 with the raw-PyMC model's (S-B); differences
  discussed in one paragraph. Any API impossibility ⇒ document what was matched.

## 7. MCMC reproducibility doctrine (AGENTS T-6)

- VR-701: Same machine + same seed ⇒ ArviZ summaries must match to 3 decimals
  (regression test using cached fits).
- VR-702: Cross-platform (CI vs local): golden tests compare summary statistics
  (posterior medians of ROAS per channel) within tolerance bands = ±0.15 × posterior
  SD, stored in `tests/golden/recovery_bands.json`, generated by
  `scripts/generate_golden_metrics.py`, regeneration only with PR justification.
  NEVER checksum draws.
- VR-703: Reports regenerate from the committed thinned posteriors (MD-051) without
  refitting: `make report` must not require sampling.

## 8. RECOVERY_REPORT.md structure (generated; order mandatory)

1. One-paragraph verdict ("the model recovers known truth under conditions X; fails
   gracefully under Y") — template with slots, no free-form spin.
2. Gate table (§3) with pass/fail per scenario.
3. Recovery plots: true vs posterior ROAS (dot + HDI whiskers, truth as ×) per
   scenario; response-curve overlays (truth line vs posterior band) — one grid per
   scenario.
4. Zero-effect channel result (S-C) with its own headline.
5. Holdout table.
6. OLS baseline comparison.
7. Cross-check summary.
8. "What this does and does not prove" — honest closing paragraph (≥ 500 chars):
   recovery on a disclosed DGP family ≠ guarantee on reality; the DGP-vs-model
   parameterization mismatch (MD-020) partially mitigates; real-world validation
   would require lift tests (Charter O-1, Future work).
