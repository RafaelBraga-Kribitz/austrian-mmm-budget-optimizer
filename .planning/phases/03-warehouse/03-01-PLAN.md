<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| committed CSV → dbt raw view | `read_csv_auto` is the only file-I/O boundary into the warehouse; everything downstream is SQL over already-typed relations |
| dbt var → `read_csv_auto` path string | Build-time Jinja interpolation of a path into SQL; the only place in this phase where a string becomes part of a query |
| dbt build process → warehouse file | The single write path to `data/warehouse/ambo.duckdb`; all application reads are read-only (plan 03-07) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Tampering | `var('data_synthetic_path')` / `var('data_real_anon_path')` interpolated into `read_csv_auto(...)` | medium | mitigate | Vars are trusted internal input only, set by the Makefile, CI, or the test suite; a comment in `dbt_project.yml`'s vars block states this explicitly and names Phase 6 intake as the first phase to introduce an externally-sourced path, at which point the assumption must be revisited (RESEARCH § Security Domain) |
| T-03-02 | Tampering | `dbt/profiles.yml` relative `path:` resolution | high | mitigate | `path: data/warehouse/ambo.duckdb` (no parent prefix) per the empirically-verified CWD-relative behavior, plus `test_warehouse_file_lands_at_settings_path` asserting the built file is exactly `settings.paths.warehouse` and that no database file appears above the repository root |
| T-03-03 | Information Disclosure | `raw_media_r` / `raw_outcome_r` / `raw_promo_r` reading a real private drop | high | mitigate | `layer_r_present: false` is the committed default (BP-D-05, ratified ADR-000 D-2); the only `true`-valued invocation in this phase is the synthetic-fixture run in plan 03-06, which also points `data_real_anon_path` at `tests/fixtures/`. AGENTS A-2 forbids any Layer R fit before the M3 gates |
| T-03-04 | Denial of Service | Concurrent `dbt build` against one DuckDB file | low | mitigate | DuckDB takes an exclusive write lock; all Phase 3 plans after wave 1 are serialized into single-file waves for this reason, and every fixture-driven build uses the separate `test` profile target with its own `AMBO_TEST_WAREHOUSE` path |
| T-03-SC | Tampering | npm/pip/cargo installs | low | accept | No new packages are installed in this phase — `dbt-core` 1.12.0, `dbt-duckdb` 1.10.1, and `duckdb` 1.5.5 were pinned and vetted at Phase 1's `01-02-PLAN.md` legitimacy checkpoint (RESEARCH § Package Legitimacy Audit: not applicable). Introducing any dbt package (e.g. `dbt_utils`) re-opens the gate and is an EB-030 ADR event |
</threat_model>
