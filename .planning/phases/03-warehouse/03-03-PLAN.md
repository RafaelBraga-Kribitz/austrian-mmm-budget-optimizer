Create four staging models under `dbt/models/staging/`. All four are views. There is no `distinct`,
no `group by`, and no `qualify row_number()` anywhere in any of them: the inputs are canonical, and
a duplicate grain key must reach the `unique` test intact so it can fail (SPEC-03 §2). Any
construct that would resolve a duplicate is the specific anti-pattern this plan exists to prevent.

`stg_media_weekly.sql` — grain week × layer × channel. A `union all` of two selects, one over
`{{ ref('raw_media_p') }}` and one over `{{ ref('raw_media_r') }}`, projecting the same eight
columns in the same order: `week_start` (date), `layer` (varchar), `channel` (varchar), `spend`
(double), `clicks` (bigint), `impressions` (bigint), `platform_conversions` (bigint),
`platform_conv_value` (double). The Layer P select applies the BP-D-03 renames —
`spend_eur` becomes `spend` cast to double (it arrives as an integer from the CSV, so the cast is
mandatory for the downstream mart contract), `platform_revenue_eur` becomes `platform_conv_value`,
and a `cast(null as bigint) as clicks` is added because Layer P media has no clicks column. The
Layer R select renames `spend_aeur` to `spend` and passes `clicks` and `platform_conv_value`
through unchanged. Neither `_eur` nor `_aeur` may survive into any output column name.

`stg_outcome_weekly.sql` — grain week × layer. A `union all` over `{{ ref('raw_outcome_p') }}` and
`{{ ref('raw_outcome_r') }}`, projecting `week_start` (date), `layer` (varchar), `revenue`
(double), `orders` (bigint). `revenue_eur` and `revenue_aeur` both become `revenue`. `promo_flag`
is deliberately not projected here — it is `stg_promo`'s grain, per SPEC-03 §2.

`stg_promo.sql` — grain week × layer. A `union all` of the Layer P branch selecting
`week_start, layer, cast(promo_flag as integer) as promo_flag` from `{{ ref('raw_outcome_p') }}`,
and the Layer R branch selecting the same three columns from `{{ ref('raw_promo_r') }}`. This is
the SPEC-03 §2 split: Layer P's promo signal comes from the outcome CSV, Layer R's from a separate
promo calendar.

`stg_calendar_weekly.sql` — grain week. A straight select over `{{ ref('season_windows') }}`
projecting all eight seed columns unchanged: `iso_year`, `iso_week`, `week_start`, `advent_flag`,
`schulbeginn_flag`, `jan_dip_flag`, `spring_flag`, `summer_lull_flag`, with the flags cast to
integer and `week_start` already typed date by the seed config from plan 03-01. No date arithmetic,
no window recomputation, no `generate_series` — the seed is the single source of Austrian-calendar
window definitions (AD-020), and this model is a typed passthrough of it.

grain tests. Use dbt's bundled `unique` generic test with a composite SQL expression as
`column_name` — the officially documented FAQ pattern — and do NOT add `dbt_utils`; introducing a
dbt package is an EB-030 ADR event for zero functional gain (RESEARCH § Alternatives Considered).
Cast `week_start` to varchar inside every concatenation expression, because DuckDB's `||` operator
will not implicitly concatenate a DATE.

  - `stg_media_weekly`: a model-level `unique` test on the expression concatenating
    `week_start` cast to varchar, `layer`, and `channel` joined by a pipe delimiter; column-level
    `not_null` on `week_start`, `layer`, `channel`, and `spend`.
  - `stg_outcome_weekly`: a model-level `unique` test on the expression concatenating `week_start`
    cast to varchar and `layer`; column-level `not_null` on `week_start`, `layer`, `revenue`,
    `orders`.
  - `stg_promo`: a model-level `unique` test on the same week-plus-layer expression; column-level
    `not_null` on all three columns, plus an `accepted_values` test on `promo_flag` with values
    `[0, 1]`.
  - `stg_calendar_weekly`: a column-level `unique` and `not_null` on `week_start`; `not_null` on
    the five flag columns.

Give every model a `description:` and every column a `description:` stating its meaning, its grain,
and — for any column that is a metric — its denominator. `spend` is per week × layer × channel in
the layer's own monetary unit; `revenue` is per week × layer in the layer's own monetary unit;
`orders` is a count per week × layer; `platform_conv_value` is the platform-reported conversion
value per week × layer × channel and is explicitly NOT a truth quantity (AGENTS T-8). These
descriptions are the single declared definition of each metric; two future consumers must not be
able to disagree about what `revenue` or `spend` means.

Create `dbt/tests/ad043_no_unit_suffix_columns.sql` as a singular test implementing D-16's strict
reading of AD-043. It selects `table_name, column_name` from `information_schema.columns` where
`table_schema` equals `{{ target.schema }}` and the table name begins with `stg_`, `fct_`, or
`dim_`, and the column name ends in `_eur` or `_aeur`. A singular test fails when it returns rows,
so a surviving suffix anywhere in staging or marts fails the build.

Two things the test must state in a header comment. First, why the raw layer is excluded: the raw
views are typed passthroughs of the producing-side CSV columns and legitimately carry `spend_eur`
and `platform_revenue_eur`; AD-043 governs staging and mart output, and the `stg_`/`fct_`/`dim_`
prefix filter is the mechanism. Second, why this reading is stricter than SPEC-03 AD-001's literal
"a dbt test fails if a mart mixes `_eur` and `_aeur`": the weaker form passes a mart that forgot the
rename entirely, which is the failure actually worth catching (D-16, also recorded in the
`docs/BUILD_LOG.md` departures entry from plan 03-01).

Because the test reads `information_schema` rather than a `ref()`, dbt cannot infer when to run it.
Add explicit `-- depends_on: {{ ref('...') }}` hint lines for all four staging models so the test is
scheduled after they are materialized. Plan 03-05 extends this same file with mart hints; this is
the one authored home for the AD-043 rule and it is never restated elsewhere.

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-03-10 | Tampering | A fixture build overwriting the real `data/warehouse/ambo.duckdb` or `dbt/target/` | medium | mitigate | Fixture runs use `--target test` with `AMBO_TEST_WAREHOUSE` and `DBT_TARGET_PATH` pointed into `tmp_path`; both tests assert the real warehouse's modification time is unchanged |
| T-03-11 | Tampering | `--vars` JSON built from a raw Windows path, producing a malformed argument | medium | mitigate | Path values are rendered with `Path.as_posix()` before JSON interpolation; the acceptance criteria require the tests to pass on Windows |
| T-03-SC | Tampering | npm/pip/cargo installs | low | accept | No new packages installed; `dbt_utils` is explicitly rejected in favour of dbt's native expression-based `unique` test (RESEARCH § Alternatives Considered), and `dbt/packages.yml` must not exist |
