Create `dbt/models/marts/fct_mmm_input.sql`, grain week x layer, materialized as a table.

Structure it as CTEs. A `media_pivot` CTE selects `week_start, layer` from
`{{ ref('stg_media_weekly') }}` and, inside a jinja `for` loop over `var('channel_taxonomy')`,
emits one aggregate per channel: sum of `spend` where `channel` equals the loop channel, wrapped in
a coalesce-to-zero and cast to double, aliased `spend_<channel>`. Group by week and layer. Never
hand-write the seven per-channel expressions — the loop over the taxonomy var is the mechanism, and
it is what keeps the taxonomy the single home for channel identity.

A `base` CTE joins `{{ ref('stg_outcome_weekly') }}` to `{{ ref('stg_promo') }}` on
(week_start, layer) and to `{{ ref('stg_calendar_weekly') }}` on week_start. The outcome model
drives the grain — one row per week x layer that has an outcome — so use inner joins to promo and
calendar. Left-join `media_pivot` on (week_start, layer), then coalesce each pivoted spend to 0.0
again at the outer level, so a week with an outcome but no media rows still emits seven zero-valued
spend columns rather than NULLs. `db.py`'s postcondition forbids NaN in spends (03_MODULES §1.3)
and the contract declares them DOUBLE.

The final select projects exactly seventeen columns, in this exact order, with these exact casts —
this list is binding and is what `_fct_mmm_input__schema.yml` and `db.py` both describe:
`week_start` cast to date, `layer` cast to varchar, `revenue` cast to double, `orders` cast to
bigint, `promo_flag` cast to integer, then the five calendar flags cast to integer in the order
`advent_flag`, `jan_dip_flag`, `spring_flag`, `schulbeginn_flag`, `summer_lull_flag` (this is
03_MODULES §1.3's order and it governs — it differs from the seed file's own column order, which is
not the contract), then the seven `spend_<channel>` columns cast to double, emitted by a second
jinja loop over the same taxonomy var so the mart column order can never diverge from the pivot.

There is no `order by` in the model — a dbt table materialization does not guarantee physical order
and the contract does not depend on it. Row ordering is asserted where it matters: `db.py`'s
accessor orders by week_start (plan 03-07) and the export writer sorts explicitly (plan 03-08).

Two consequences of the taxonomy pivot must be understood rather than "fixed". `spend_other` will
be exactly 0.0 on every Layer P row, because `other` is Layer-R-only under BP-D-04 and no Layer P
media row carries that channel. That is correct and intended — a structurally absent channel is
zero-filled. Distinguishing it from a present-but-ineffective channel (S-C's `display_video` has
real spend and zero true effect by VR-304 design) is `dim_layer.channels_present`'s job in plan
03-05, not this model's. Do not add a filter, a NULL, or a sentinel to make the two look different
here.
