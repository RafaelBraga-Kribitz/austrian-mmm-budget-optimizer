<objective>
Build `dim_layer` with the `channels_present` derivation that lets Phase 4 tell a structurally
absent channel apart from a present-but-ineffective one, and make that distinction a checked fact
with a both-directions test.

Purpose: `other` is Layer-R-only under BP-D-04, so every Layer P row carries a structurally zero
`spend_other`. Meanwhile S-C's `display_video` has real spend (92,193 total) and zero true effect —
that is the VR-304 design. If the model cannot tell those two apart, MD-040's channel-agnostic
priors end up fitting a coefficient for a channel with no data at all. `channels_present` is the
mart's mechanism for saying which columns are real, and D-14 is what makes a pivot bug that leaks
spend into an absent column fail at build time rather than at fit time.

Output: one contract-enforced dimension table, one both-directions singular test, and the extension
of the strict AD-043 test's coverage to the mart layer.

Standing obligations (D-18, D-19): tests ship with what they verify. `channels_present` and its
derivation are on the D-19 **never-shed** list; the `dim_layer` enforced contract is shed item 2 and,
if shed, must be written into `docs/BUILD_LOG.md` first — note that shedding the *contract* never
means shedding the *column*.
</objective>

## Identity model: the layer is primary, not an annotation

**Detector result:** the deterministic assumption-delta scan over this phase's ROADMAP scope
returned `detected: false` with zero signals, so the advisory checkpoint did not fire. This block is
therefore a **recorded planner design decision, not a checkpoint output** — it is written down
because the phase's own content raises the identity question the checkpoint exists to surface, and
because the planning brief specifically asked for the BP-D-05 staleness to be settled explicitly
rather than silently re-decided.

**The seam:** Phase 2 produced three scenario directories that Phase 3 must represent as a plural,
first-class set (`P-SA`, `P-SB`, `P-SC`), and `dim_layer` introduces `layer` as a table of its own.
Simultaneously `layer_r_present` makes an entire fourth layer conditional and currently absent
(BP-D-05).

**Noun now primary:** `layer`.

**Decision: promote.** `layer` is a first-class key on every mart grain — `fct_mmm_input` is keyed
(week_start, layer), `fct_platform_reported` is keyed (week_start, layer, channel), and `dim_layer`
is the identity table those grains reference. AD-002 already names `layer` a universal key, and this
plan makes that structural rather than incidental. Layer P is one *variant* of the general layer
concept (monetary_unit EUR, source_tag GROUND-TRUTH, channels from the six-channel synthetic set),
and Layer R is another variant (aEUR, REAL-ANON, manifest-matched channels) — Layer R is not bolted
onto a Layer-P-shaped world. Concretely: no mart may carry a Layer-P-specific column, no monetary
unit may appear in any column name (that is exactly what D-16's strict AD-043 enforces), and
`channels_present` is per-layer rather than a global constant, so a layer with a different channel
set needs no schema change.

**Rationale:** the alternative — treating Layer P as the default and adding Layer R alongside —
would put the unit back into column names and make the M4 flip a schema change rather than a flag
flip. D-20's fixture-exercised branch (plan 03-06) only makes sense against a promoted identity
model.

**BP-D-05 note:** the ROADMAP's Phase 3 note saying `layer_r_present: false` is "a blueprint default,
not a ratified decision — accept or override it explicitly at task time" is **stale**.
`docs/ADR/ADR-000` D-2 ratified BP-D-01…BP-D-20 wholesale and states the Definition-of-Ready
accept/override item is satisfied for all twenty by that ADR. `layer_r_present: false` is binding and
is not re-litigated here. Plan 03-09 corrects the stale ROADMAP note.
</assumption_delta_decision>

Create `dbt/models/marts/dim_layer.sql`, grain layer, materialized as a table.

A `present` CTE selects the distinct (layer, channel) pairs from `{{ ref('stg_media_weekly') }}` —
this is D-13's derivation: a channel is present if it has rows in staging for that layer. Do NOT
derive presence from nonzero spend. A nonzero-spend derivation silently reclassifies a real channel
that has a zero-spend period, and on Layer R it could disagree with the intake manifest, putting
AD-044 in the position of failing for a legitimate reason.

An `ordinal` CTE materializes the taxonomy order as a two-column inline relation of (channel,
position) pairs, generated by a jinja loop over `var('channel_taxonomy')` using the loop index as
the position. This is what makes BP-D-19's "canonical order" a mechanism rather than an assumption.

A `joined` CTE inner-joins `present` to `ordinal` on channel, then aggregates per layer with
DuckDB's string aggregation, comma-delimited and ordered by the position column, producing
`channels_present`. An inner join is deliberate: a source channel outside the taxonomy would be
dropped here, which is a real possibility for Layer R at M4 — the AD-044 test (plan 03-06) is what
catches that case, and silently listing an unknown channel in this column would defeat it.

A `weeks` CTE counts distinct `week_start` per layer from `{{ ref('stg_outcome_weekly') }}`.

The final select joins `weeks` to `joined` on layer and projects exactly five columns in this order
with these casts: `layer` cast to varchar; `weeks` cast to bigint; `channels_present` cast to
varchar; `monetary_unit` cast to varchar, derived from the layer value — the literal `EUR` for any
layer beginning with the Layer P prefix, `aEUR` otherwise; `source_tag` cast to varchar, derived the
same way — `GROUND-TRUTH` for Layer P, `REAL-ANON` otherwise. Drive the grain from `weeks` (the
outcome model) and left-join `joined`, coalescing `channels_present` to an empty string, so a layer
with outcome rows but no media rows still produces a row rather than vanishing.

Do not fabricate a Layer R row when `layer_r_present` is false. With the flag false the staging
unions contribute zero Layer R rows, so `dim_layer` naturally contains exactly three rows. Absence is
the correct representation of an absent layer; a placeholder row with null or zero fields would make
`dim_layer` lie about what the warehouse contains.

Create `dbt/models/marts/_dim_layer__schema.yml` with `contract: {enforced: true}`,
`materialized: table`, and the five columns declared with `name` and `data_type` — `varchar` for
layer, channels_present, monetary_unit and source_tag; `bigint` for weeks. No inline `constraints:`
block, for the same DuckDB support reason as plan 03-04. Add column-level `not_null` on all five, a
`unique` test on `layer`, and `accepted_values` tests on `monetary_unit` with values EUR and aEUR and
on `source_tag` with values GROUND-TRUTH and REAL-ANON.

Give the model and all five columns a `description:`. `channels_present`'s description is the most
load-bearing text in this plan and must state all four of: the derivation rule (source-row presence,
never nonzero spend); the format (comma-joined string in SPEC-02 §5.2 taxonomy order, BP-D-19); the
binding consumer instruction that model code iterates this column and never the seven spend columns
directly (D-13); and the reason, that a structurally absent channel and a present-but-ineffective
channel must not look the same to the model. `monetary_unit`'s description must state that it is the
single home for the unit fact, that no mart or staging column name may carry a unit suffix (AD-043,
D-16), and that `weeks` is a count with the week as its denominator.
